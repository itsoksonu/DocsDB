## Phase 0 — Orientation & baseline

**Stack.** npm workspaces-style monorepo (root `package.json` with `concurrently`).
`server/` is Express 4 + Mongoose 8 + Redis 4 + Bull 4 + Socket.io, ESM (`"type": "module"`),
Node 22. `frontend/` is Next.js 14 pages-router + React 18 + Tailwind, deployed to Netlify
(`netlify.toml`). Storage is S3; auth is Google OAuth only (no password auth anywhere —
so bcrypt/reset-token/login-enumeration findings are not applicable). AI features use
Gemini/Groq/HuggingFace; payments use Stripe Connect.

**Findings from orientation itself (all fixed):**

- **No linter, formatter or type-checker was configured**, in either package, despite both
  declaring a `lint` script. `server/package.json` shipped `eslint` as a devDependency with
  no config file. Severity: **medium** — this is why the four genuine bugs in Phase 3 below
  went unnoticed.
- **`npm test` was vacuously green-or-red.** The only test file is `.mjs`, which jest's

## Phase 1 — Security

### Critical

**1. Account takeover via client-supplied email — `server/services/OAuth/routes.js:60`**
`const userEmail = email || verifiedUserInfo?.email;` — `email` came from `req.body`. Anyone
holding *their own* valid Google ID token could post
`{accessToken: <their token>, email: "victim@example.com"}`. No provider link existed for
their `sub`, so `User.findOne({ email })` resolved the **victim**, line 86 permanently linked
the attacker's Google identity to that account, and lines 104–113 issued victim JWTs.
`email_verified` was never checked either.
**Fixed:** identity is now derived solely from the verified ID token (`sub`, `email`, `name`,
`picture`); `verifyGoogleToken` throws unless `payload.email_verified === true`. `providerId`
is still accepted in the body for client compatibility but ignored.
Frontend counterpart fixed at `frontend/src/contexts/AuthContext.js:156` — it no longer
`atob`-decodes the credential and posts the fields separately.

**2. IDOR on every document — `server/services/download/routes.js:104`**
`completeDownloadSession(sessionId, userId, adCompleted)` validated session *ownership* but
never compared `session.documentId` to `req.params.id`. An attacker created a session against
their own document (which sets `adRequired:false, timerDuration:0`) and redeemed it for **any**
`:id`, bypassing `validateDownloadRequest` and `isViewable()` entirely — yielding private,
unprocessed, and other users' paid documents.
**Fixed:** the document id is passed into `completeDownloadSession` and compared against the
session (`downloadManager.js`); mismatch returns 403.

**3. Arbitrary S3 object read via avatar — `server/services/auth/routes.js:21`**
Any string not starting with `http` was written straight to `user.avatar`, and
`s3.generateViewUrl` then returned a presigned GET for it. Setting `avatar` to
`uploads/<otherUserId>/<ts>-<uuid>.pdf` (keys are enumerable from document responses) leaked
arbitrary tenant files.
**Fixed:** `isOwnAvatarKey()` restricts the value to `^avatars/<callerId>/[\w.-]+$`; anything
else is a 400.

**4. Unauthenticated SSRF — `frontend/src/pages/api/proxy-image.js:11`**
`axios.get(req.query.url)` with no allowlist, protocol check, redirect limit, timeout or size
cap, and the response body returned to the caller. Reachable in production
(`ShareCard.jsx:112,230`). `/api/proxy-image?url=http://169.254.169.254/latest/meta-data/...`
reads IMDS; `http://localhost:3001/...` reaches the internal API.
**5. Stored XSS on our own origin — same file, line 15.** The upstream `content-type` was
reflected verbatim, so any attacker URL returning `text/html` was served as HTML from our
origin — and cached `immutable` for a year.
**Fixed:** extracted the destination allowlist that `pdf-proxy.js` already had into
`frontend/src/lib/s3Allowlist.js` and applied it to both routes; added an image-only
content-type allowlist, `nosniff`, `maxRedirects: 0`, a 15s timeout and a 10 MB cap. SVG is
served as `application/octet-stream`. `pdf-proxy`'s allowlist now **fails closed** when the
bucket env var is unset (it previously degraded to "any `*.amazonaws.com`").

## Phase 2 — Memory & resource leaks

### Critical

**`shared/utils/documentIndex.js:254` — unbounded passage cache (guaranteed OOM).**
Eviction was weighted purely by vector length: `floats += passage.embedding?.length || 0`.
But the text-only load path selects no vectors (`loadPassages` uses
`.select("index label text")` when `model` is null, and `buildIndex` writes
`embedding: null` explicitly), so `floats === 0`, `cachedFloats` never rose, the eviction
loop never ran, **and there was no entry-count cap at all**. Every short / unembedded document
ever opened in Ask AI — the common case — parked up to `MAX_EXTRACT_CHARS` (600 000 chars ≈
1.2 MB of UTF-16) in the Map forever, on an instance the file is explicitly tuned to keep
under 512 MB.
**Fixed:** added `MAX_CACHED_DOCUMENTS = 50` and folded an entry-count condition into the
eviction loop.

**`shared/utils/documentProcessor.js:1117` — temp file and S3 socket leaked on every failed download.**
`downloadFromS3` never returns `tmpPath` on failure, so `processDocument`'s
`finally { cleanupTempFile(filePath) }` saw `undefined` and cleaned nothing — the partial file
stayed in `os.tmpdir()` permanently, once per retry (`attempts: 3`), and the unread `Body` held
a socket. **Fixed:** the catch now destroys the body and unlinks the temp path before rethrowing.

### High

- **`documentProcessor.js:115` — the global `console.log`/`console.warn` patch was not
  reentrant.** Four Bull processors are registered, each with default concurrency 1, so up to
  four jobs run in one process; `extractPDFWithOCR` and `ocrPdfPages` both call
  `runWithPdfWarningsSuppressed`. The second caller captured the *already-patched* function and
  restored **that** as the permanent `console.log` — leaving suppression on forever and
  retaining a closure per overlap. Fixed with a depth counter that makes nested calls
  pass-through.
- **`shared/utils/counters.js:113` — orphaned `:draining:` Redis keys with no TTL.** The
  `finally { del(draining) }` only wrapped `applyDeltas`, so `hGetAll` throwing *and* the
  empty-deltas early return at line 127 both leaked a timestamped key holding real counter
  data. Moved the delete into the outer `finally`.
- **`shared/utils/downloadManager.js:268` — unbounded Redis lists with a TTL refreshed on every
  write.** `expire(key, 86400)` after each `rPush` meant an active user or a busy NAT address
  never expired, and there was no `LTRIM` — pruning only happened incidentally inside
  `getRecentDownloadsCount`. Replaced with a single `MULTI` doing
  `rPush` + `lTrim` + `expire … NX`.
- **`services/fetcher/cron.js:62` and `fetcher/routes.js:45` — `fetch-documents` jobs never
  removed from Redis.** Both enqueued with `{ jobId }` only — no `removeOnComplete`,
  `removeOnFail`, `attempts` or `timeout`, unlike every other job type in the file — and the
  handler returns a payload listing up to 100 documents, stored in the job hash forever. A
  daily cron over five categories retained ~1 825 large records a year. Added
  `FETCH_JOB_OPTIONS` with age-based removal (the polling endpoint needs the record briefly).

### Medium

- **`server.js:169` — graceful shutdown drained nothing.** `server.close()` was called without
  `await` and followed immediately by `process.exit(0)`, cutting live responses off mid-flight.
  The Bull queue (three Redis connections plus its stalled-check intervals), the Socket.io
  server (open websockets mean `server.close()` never calls back), and the node-cron task were
  never closed at all. **Rewritten:** re-entrant guard, `fetcherTask.stop()`, `closeSocket()`,
  awaited `server.close()`, `processDocumentQueue.close()`, `stopCounters()`,
  `databaseManager.disconnect()`, all behind a 25s `SHUTDOWN_TIMEOUT_MS` hard deadline.
  Added `closeSocket()` to `shared/utils/socket.js` (`getSocketIO()` throws when uninitialised,
  which shutdown must not).
- **No `unhandledRejection` / `uncaughtException` handlers anywhere.** Any escaped rejection
  took the process down with the Redis counter buffer undrained. Added both; the latter routes
  through the new shutdown path.
- **`shared/queues/processQueue.js:294` — the `failed` handler could crash the process.**
  `job.opts.attempts` and `job.name` were read unguarded, and every job type sets
  `removeOnFail: true`, so Bull can emit `failed` with a partially-collected job. A throw inside
  an EventEmitter handler is an uncaught exception. Added optional chaining in both handlers.
- **No job `timeout` on any job type.** A wedged Tesseract or pdf.js call held its worker slot
  indefinitely. Added `timeout: 10 min` to the three heavy option sets, 30 min for fetch jobs.
- **`shared/database/connection.js:31` — Redis client had no reconnect strategy, connect
  timeout, or bounded offline queue.** node-redis retries indefinitely by default (reconnect
  storm), and `disableOfflineQueue` defaulted to `false`, so commands issued while disconnected
  piled up in-process. Added a backoff `reconnectStrategy`, `connectTimeout: 10s`,
  `disableOfflineQueue: true`. Also added `mongoose.connection.on("error"/"disconnected")`
  listeners — the existing try/catch only covered the *initial* connect, so a post-startup
  failure was silent.
- **`feed/routes.js:617` — `redis.keys()` on every interaction write.** `KEYS` is O(keyspace)
  *and* blocks single-threaded Redis, and this runs at up to 120 req/min per user. Replaced with
  `scanIterator` over the two known key patterns, deleting in batches of 100. (The surrounding
  block was six lines of "this is expensive, TODO" comments and then did it anyway.)
- **`shared/utils/downloadManager.js:319` — dead `cleanupExpiredSessions()`** doing a
  full-keyspace `KEYS` scan. Exported, never called, and redundant since sessions already carry
  a TTL. Deleted.
- **Whole documents loaded into memory on request paths** — `documentPreview.js:116` and
  `documentText.js:163` both `getObjectBuffer` with no size guard while uploads are allowed up
  to 100 MB, and there is no concurrency limit. The `MAX_*` constants bound the *output*, not
  the input. Added 25 MB input ceilings using the `sizeBytes` already on the Document.
- **`documentOcr.js:121`** and **`documentProcessor.js:1095`** — temp files written outside the
  `try` whose `finally` unlinks them, so a failed write leaked (OCR retries up to 40 times).
  Both now clean up on the failure path.

### Frontend

- **`GlobalUploadWidget.jsx:141` — `setTimeout` in an effect with no cleanup, deps `[uploads]`.**
  Every subsequent `uploads` change queued another timer, so `resetUploads()` and
  `router.push()` fired repeatedly and could fire after navigating away. Added `clearTimeout`.
- **`GlobalUploadWidget.jsx:54` — the socket was never disconnected.** This component is mounted
  in `_app.js` and never unmounts, so the unmount-only cleanup never ran: once any upload
  processed, the websocket stayed open for the entire session and `joinedRoomsRef` grew
  unbounded. Now torn down when nothing is left processing.
- **`useGoogleAuth.js:28` — a 100 ms `setInterval` and a 5 s `setTimeout` in an effect returning
  `undefined`.** Unmounting inside that window left the interval calling `setState` on a dead
  component. Hoisted the ids and added a cleanup.
- **`search.jsx:151` — the `IntersectionObserver` was disconnected only when the ref callback
  re-ran**, so the last one outlived the page. Added an unmount cleanup.
- **`explore.jsx:161` — `useCallback(debounce(...))`** created a new debounced function on every
  filter change without cancelling the previous one, so a pending keystroke pushed a route built
  from stale filters, and nothing cancelled on unmount. Switched to `useMemo` + a cancel effect.

### Post-build follow-up

Running the build locally exposed three things the sandbox could not:

**1. `postbuild` failed — the deploy was broken. (high, fixed)**
`frontend/next-sitemap.config.js` used `module.exports` while `frontend/package.json` declares
`"type": "module"`, so the file is an ES module and `module` is not defined:

```
❌ [next-sitemap] ReferenceError: module is not defined in ES module scope
```

next-sitemap loads its config with `await import(path)` and reads `.default`
(`dist/esm/parsers/config-parser.js:52`), so `module.exports` could never work. Because
`postbuild` runs as part of `npm run build`, the whole build script exited non-zero — meaning
**Netlify deploys were failing after a successful compile**, and no sitemap or `robots.txt` was
being generated. Converted to `export default` and verified the config now loads with the exact
mechanism next-sitemap uses (correct `siteUrl`, `generateRobotsTxt`, `exclude`, and
`additionalSitemaps`).

Checked the sibling config files for the same class of bug: `postcss.config.cjs` is correctly
`.cjs`, and `tailwind.config.js` uses `module.exports` but works because Tailwind uses its own
CJS-capable loader rather than native `import()` — the successful build confirms it. Left alone.

**2. VS Code reported `Parsing error: Cannot find module 'next/babel'`. (low, fixed)**
Caused by the ESLint config I added in Phase 5. The ESLint *extension* runs from the workspace
root `D:\DocsDB`, where `next` is not installed, so `eslint-config-next`'s parser cannot resolve
`next/babel` and every `.jsx` file shows a false parsing error. The CLI is unaffected — `next lint`
runs inside `frontend/` and passed in the build above. Added `.vscode/settings.json` pinning

**3. `⚠ Unrecognized key(s) in object: 'runtime' at "experimental"` — resolved, with the
production break explained. (low)**

| Occurrences in `next/dist/server/config-schema.js` | **0** | 1 |

### `xlsx` → `exceljs`, done

The last unfixable advisory. `xlsx` (SheetJS) has no patched release for
GHSA-4r6h-8v6p-xvw6 (prototype pollution) or GHSA-5pgg-2g8v-p4x9 (ReDoS), and it was

`documentPreview.buildXlsxPreview`, `documentText.extractXlsx`,
`documentProcessor.extractFromXLSX`, `documentProcessor.getXLSXPageCount`, and the
`xlsx` branch of `thumbnails.generateContentThumbnail`.

Between them those five wanted only three things, so rather than five separate ExcelJS
migrations there is now one **`shared/utils/spreadsheet.js`** exposing `readSheetRows`
(arrays of strings), `readSheetsAsCsv` (text extraction) and `countWorksheets` (page count),
each accepting a Buffer or a path. One place to get cell handling right, one place to test it.

**`cell.text` is a trap, and a comparison harness caught it.** Before writing anything I built
a fixture covering every awkward cell type and printed what both libraries actually produce.
ExcelJS's own `cell.text` — the obvious choice — is wrong twice over:

| Cell | `cell.text` gives | `cellToText` gives |
|---|---|---|
| Date `2024-01-15T00:00:00Z` | `"Mon Jan 15 2024 05:30:00 GMT+0530 (India Standard Time)"` — locale **and** timezone dependent | `"2024-01-15"` |
| `{formula:"1/0", result:{error:"#DIV/0!"}}` | `"[object Object]"` | `"#DIV/0!"` |

Dates are formatted from UTC getters deliberately: local formatting would shift the day either
side of midnight depending on server timezone. The normalizer mirrors the semantics of the
client-side `cellToText` in `SheetViewer.jsx`, so a server-generated preview and the
interactive viewer agree on what a cell says.

**It also fixes a live display bug.** The old array path used
`sheet_to_json(sheet, { header: 1 })` with no `cellDates`, which returns Excel **serial
numbers** for dates — the harness showed `45306` where `2024-01-15` belonged. Every XLSX
preview and thumbnail has been rendering raw serials in date columns. They now render as dates.

**One deliberate behaviour difference:** number formats are no longer applied, so a cell
displayed as `$9.50` extracts as `9.5`. For search and AI context the underlying value is more
useful, and applying formats would mean adding a format library server-side.

**Tests: 24 new cases** in `shared/utils/__tests__/spreadsheet.test.mjs`, built against a real

### `uuid` — dependency dropped rather than upgraded

After the `xlsx` migration the server was down to one advisory
(GHSA-w5hq-g745-h8pq) reported from three places: our direct `uuid@9`, plus nested
copies under `bull` and `exceljs`.

The advisory is a bounds check in **v3/v5/v6 when a `buf` argument is passed**. All six
call sites in this codebase were bare `uuidv4()` — v3/v5/v6 are never used at all, let
alone with a buffer. So it was never reachable. It is now gone anyway, in two steps:

**1. The direct dependency was removed, not bumped.** Node has `crypto.randomUUID()`
built in, and it emits the same RFC 4122 v4 string, so the six call sites
(`s3.generateFileKey`, the fetcher's temp dir / file / S3 keys, and two job ids) now use
it. `fetcher.js` already imported `crypto`; the other three files gained the import. That
removes a dependency outright rather than trading one version of it for another, and it
matches how `downloadManager.generateSessionId` was already fixed earlier in this audit.
Verified that generated keys keep their exact previous shape — including that the avatar
key still satisfies the `^avatars/<userId>/[\w.-]+$` scope check added in Phase 1.

**2. The two transitive copies are pinned via `overrides`.** Checked before pinning rather
than hoping: `bull` does `require('uuid')` → `uuid.v4()`, `exceljs` does
`const {v4} = require('uuid')`, and `uuid@11.1.1` still publishes a CommonJS export
(`"require": "./dist/cjs/index.js"`). So both keep working. The pin is deliberately
`^11.1.1` and **not** latest, because uuid 12+ drops CommonJS and would break both
consumers — which is also why `npm audit fix --force`, offering `uuid@14`, was the wrong
button.

The `overrides` block carries a `//overrides` note in `package.json` explaining that
reasoning, so the next person doesn't "helpfully" bump it.

**Expected after `npm install`: 0 vulnerabilities on the server** (from 69 at the start of
this audit).

### The hooks refactor (frontend)

The `react-hooks/exhaustive-deps` warnings could not be silenced by editing dependency
arrays — doing literally what the rule asks would have caused infinite render loops. Every
one is now fixed at the root instead. Three distinct causes:

**1. Two loop hazards, fixed by moving bookkeeping out of state.**
`search.jsx` had `performSearch` listing `page` as a dependency *and* calling `setPage`;
`explore.jsx` had the same shape with `searchPage`; `profile/index.js` with `nextCursor`.
Each would have looped as soon as an effect depended on the callback: effect → setState →
new callback identity → effect → … None of the three values was ever rendered — they were
only read back by the next request — so all three became refs (`pageRef`, `searchPageRef`,
`nextCursorRef`). That removes the loop at the root, and drops three needless re-renders per
search.

**2. Context functions were unstable, so effects depending on them were unsafe.**
`GlobalUploadWidget` names `updateUpload` and `resetUploads` in effect dependency arrays,
but `UploadContext` rebuilt every handler on each render — listing them would have torn down
and rebuilt the websocket on every render. So `UploadContext` is now memoized: every handler
is a `useCallback` and the provider value a `useMemo`. Because all its state updates use the
functional form of `setState`, most handlers need **no** dependencies and are stable for the
lifetime of the app. This also delivers the provider-value memoization that was previously
listed as deliberately-not-changed.

**3. `AuthContext` had a mutex that did not work.**
`refreshTokenSilently` guarded itself with `if (refreshing)` where `refreshing` is *state* —
and `setState` is asynchronous, so two calls landing in the same tick both saw `false` and
both fired a refresh. The guard is now a ref (`refreshingRef`), with the state kept only
because it is published on the context. `user` is likewise mirrored into a ref, so the
13-minute refresh interval is created **once** instead of being destroyed and rebuilt on
every change to `user`.

**Two false positives, fixed honestly rather than suppressed.**
`jsx-a11y/alt-text` fired on `<Image size={24} />` in `profile/index.js` — that is a lucide
*icon*, not an `<img>`; the rule matches on the component name. Imported as `ImageIcon`
instead, which also stops it being mistaken for `next/image`. And the one
`eslint-disable-next-line react-hooks/exhaustive-deps` I had left in `explore.jsx` was
removed: `pushRoute` is already a stable `useCallback`, so it can simply be listed.

**One duplicate-fetch bug fixed along the way.** `profile/index.js` had two effects both
calling `loadDocuments(true)` — one debounced on search, one on tab change — so mounting the
page and every tab switch fired two identical requests. The tab effect now only resets list
state; loading is left to the single loader effect, which re-runs anyway because `activeTab`
is one of `loadDocuments`' dependencies.

**A TDZ trap worth knowing about.** A dependency array is evaluated *during render*, so a
`const` arrow function declared further down the component is still in its temporal dead zone
when an earlier effect names it — a `ReferenceError`, not a warning. Four files needed
declarations reordered for this (`AuthContext`, `profile/index.js`, `[slug].jsx`,
`moderation.jsx`), and in `[slug].jsx` three `useState` calls that sat *below* the effects
were moved up with the rest of the state.

### Second pass: the remaining frontend warnings

A local `npm run lint` confirmed the refactor above landed (none of those files reappeared)
and surfaced the rest, plus one runtime warning that mattered more than any of them.

**A `<title>` hydration bug — the only real defect in this batch. (medium)**
Next reported *"A title element received an array with more than 1 element as children …
hydration will likely fail and fall back to client rendering."* Three pages wrote
`<title>{expression} - DocsDB</title>`, which is two children — an expression plus a string
literal — and therefore an array of text nodes rather than the single text node the browser
requires: `document/[slug].jsx:245`, `explore.jsx:347`, `search.jsx:286`. All three now
build the whole string in one expression. This is worth more than the lint count: a
hydration fallback silently costs the SSR benefit on the document page, which is the page
that matters most for SEO here.

**Four more `exhaustive-deps`, and the same root cause twice more.**
`DesktopNavbar` and `Footer` both name `initializeGoogleOneTap` in an effect, but
`useGoogleAuth` returned fresh functions and a fresh object on every render — so listing it
would have re-initialised Google One Tap continuously. The hook is now memoized
(`useCallback` throughout, `useMemo` on the returned object), as is **`AuthContext`**, whose
value object and four handlers (`oauthLogin`, `updateUser`, `handleGoogleOAuth`, `logout`)
were also rebuilt each render. `handleGoogleResponse` in both components then becomes a
stable `useCallback`. `index.js` and `report/[id].jsx` were the straightforward remaining
two.

That makes three providers/hooks memoized in total — `UploadContext`, `AuthContext`,
`useGoogleAuth`. In every case the unstable value was the *reason* the consuming effect
could not list its dependencies honestly, so fixing the provider was the actual fix.

**18 unescaped entities across 10 static pages**, escaped to `&apos;` / `&ldquo;` /
`&rdquo;`. Applied by script with a one-match assertion per replacement, so a silent miss or
an accidental double-hit would fail loudly rather than corrupt a file. One reported
occurrence was deliberately left: `report/index.jsx:261`'s `"Submit Report"` is a JavaScript
string inside a ternary, not JSX text — ESLint never flagged it, and escaping it would have
printed `&ldquo;` to the screen.

**Two internal links** (`report/index.jsx` → `/dmca`, `upload.jsx` → `/terms`) converted from
`<a href>` to `next/link`, which is a real behaviour improvement: they were doing full page
reloads instead of client-side navigation.

**A third stub, found on the way (low).** `feedGenerator.js:103` —
`getRelevanceSort(_userId)` is a documented placeholder that ignores the user and returns
popularity ordering, so `sort=relevant` is silently `sort=popular`. Unlike the two stubs
above this one is honest — it returns a real sort, not invented numbers — so it is noted
rather than flagged. `injectAds` likewise ignores its `userId`, so ad selection is not
personalised.

**One self-inflicted error, caught by the linter.** Removing `execAsync` and `__dirname`
left their imports dead, and I deleted the imports while the declarations were still
referencing them — `no-undef` flagged it immediately. Fixed before it went anywhere. That
is the tooling from Phase 0 paying for itself twice in one session.

**`server/.env` was never committed** — `git log --all --full-history -- server/.env` returned
empty. The credential exposure is therefore local-only, which is the good outcome. Rotation is
still worth doing if that file has ever been shared, backed up, or synced.

## Deliberately not changed

| Finding | Why not |
|---|---|
| **Rotate the credentials in `server/.env`** | Not a code change, and only you can do it. Live AWS access keys, a MongoDB Atlas URI with credentials, a Redis Cloud password, a Google client secret, and OpenAI / HuggingFace / Cohere / Gemini / DeepSeek / Groq / VirusTotal keys sit in plaintext in the working tree. **Confirmed never committed** (`git log --all --full-history -- server/.env` is empty), so this is local-only exposure — the good outcome. Still worth rotating if that file has ever been shared, backed up or synced, and the `.gitignore` fix now prevents a future `git add -A` from committing it. |
| **No Content-Security-Policy on the frontend** | `next.config.mjs` sets `nosniff`, `X-Frame-Options` and the dead `X-XSS-Protection`, but no CSP — so the JSON-LD XSS fixed in Phase 1 had no second line of defence, and the unfixable `echarts` XSS in `pptx-preview` has none now. A starting policy: `default-src 'self'; script-src 'self' 'unsafe-inline' https://accounts.google.com; img-src 'self' data: https:; connect-src 'self' <API origin> https://accounts.google.com; frame-ancestors 'none'`. Not added blind because the exact `script-src`/`connect-src` needed by Google Sign-In and the API origin depend on your deployment, and a wrong CSP breaks login silently. |
| **Refresh-token revocation / rotation family** | Refresh tokens are stateless 30-day JWTs, so `/logout` is cosmetic and a stolen token stays valid for 30 days with no reuse detection. Fixing it properly means a `jti` store with family tracking — a design decision about session storage, not a patch. I did close the privilege-escalation half of it (claims now come from the DB). |
| **Mounting the Stripe webhook** | `shared/integrations/stripe.js` exports `handleStripeWebhook` and `verifyWebhookSignature`, and **nothing mounts them** — no route exists. Consequence: `wallet.kycStatus` is only ever written by `handleAccountUpdated`, so the KYC gate at `monetization/routes.js:141` can never be satisfied, and payout success/failure is never reconciled. Wiring this up needs `express.raw` mounted *before* `json()`, an `event.id` dedupe store, and a decision about which events you care about. That is a feature, not a fix. |
| **Cookie `secure` / `sameSite` gated on `NODE_ENV`** | Any staging or preview deploy ships the 30-day refresh token over plain HTTP with `sameSite: lax`. Hardcoding `secure: true` breaks local development over HTTP, and scoping the cookie's `path` to the refresh endpoint requires a matching change in `clearCookie` and possibly the frontend. Needs your call on how staging is configured. |
| **`app.set("trust proxy", 1)`** | Blindly trusts exactly one `X-Forwarded-For` hop. With a different hop count, or any direct exposure, `req.ip` becomes attacker-controlled — defeating the IP-keyed limiter, the IP download cap, and `reporterIp` attribution. The correct value is your load balancer's actual hop count or CIDR, which I do not know. |
| **Access token in `localStorage`** | XSS-readable. Moving it to a module-level variable in `APIService` is straightforward (refresh-on-load already repopulates it from the HttpOnly cookie) but changes the auth lifecycle across `AuthContext` and every consumer — worth doing, worth doing deliberately. |
| **Admin pages gated client-side only** | `/admin/*` HTML and JS chunks are served to anyone and the redirect happens after hydration. Currently acceptable because every admin API call is server-authorised, so no data leaks — but the fix (middleware or `getServerSideProps` session checks) is a routing change. |
| **OCR re-parses the whole PDF once per page** | `ocrPdfPages` calls `pdfToImg(filePath, { pages: [page] })` in a loop, so pdf.js re-parses the document up to 60 times per pass, up to 40 passes. Real waste, but fixing it needs a `pdfToImg` call taking a page *range* — a rewrite of that function, not a one-line change. |
| **~30 `react/no-unescaped-entities` and 4 `no-html-link-for-pages` warnings** | Pre-existing, cosmetic, and spread across static content pages. Fixing them would have produced a large diff unrelated to anything in this audit. Left as warnings so they are visible. |
| ~~`react-hooks/exhaustive-deps` warnings~~ | **Now done properly** — see the section below. |
| **The two `Math.random()` stubs** (content moderation, download statistics) | Marked with unmissable `STUB` headers, not implemented. Implementing them is a product decision: moderation needs a provider choice *and* a policy for what a flag does (quarantine? queue? reject?), and the statistics endpoints need a decision about which of the three existing data sources is authoritative. I would be inventing requirements. I also deliberately did **not** change their HTTP responses to 501 — tempting, since nothing consumes them, but that is a silent behaviour change to a live endpoint on my own judgement, which is exactly what you asked me not to do. Flagged instead. |
| **`checkSensitiveContent` option accepted and ignored** | Part of the moderation stub above. Removing the option or wiring it up both presume an answer about what the check should do. |
| **`jest` and `supertest` devDependencies** | Now unused (no jest tests exist). Left in place in case integration tests are planned; flagging rather than removing. |
| **Pre-existing CRLF conversion across ~100 files** | Already in the working tree when I started. Reverting it is not mine to decide, and normalising it would bury every real change. Review with `git diff --ignore-cr-at-eol`. |
